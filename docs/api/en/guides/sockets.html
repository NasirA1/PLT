    Sockets: talking over the network

    On this page

    Part of the Thunder SDK reference.

    A Thunder program can talk to a program on another computer (or to a web server, or to itself) through sockets. One side listens on a port, the other connects to that computer and port, and then text flows both ways until one side closes. That is all a chat program, a game server or a web browser does underneath.

    import "sockets"

with server = tcp.listen("", 5000)               # wait for callers on port 5000
    with connection = tcp.accept(server)         # ... here comes one
        println(connection.receive_line())       # what it said
        connection.send_line("hello back")       # the answer
# here "with" has closed the connection, then the listener
    import "sockets"

with connection = tcp.connect("192.168.1.20", 5000)  # the computer running the program above
    if connection == nothing
        println("cannot connect: ", socket.error())
    else
        connection.send_line("hello there")
        println(connection.receive_line())            # "hello back"

    Sockets come from a native module: the C++ library thunder_sockets (lib/native/sockets/thunder_sockets.cpp), built with the toolchain and sitting next to thundervm. The Thunder file sockets.th declares the socket.Socket object - every per-socket operation is one of its methods - and four modules on top of it - tcp, udp, socket and host - so a program needs only import "sockets": thunderc finds the SDK's files in lib/thunder/<language> next to itself. In the IDE this document is under Help > Sockets reference; sample 38 (samples/en/38_sockets.th) runs a server and a client in one program.

    1. The idea in five lines#

    Word Meaning
    addresswhich computer: "127.0.0.1" is always this one, "192.168.1.20" a neighbour, "example.org" a name the network looks up
    portwhich program on that computer: a number from 1 to 65535; 0 asks the system for any free one
    TCPa connection: text arrives complete and in order, both ways, until one side closes
    UDPsingle messages (datagrams) to any address, with no connection; quick, but one may be lost
    socketa socket.Socket: what a program holds for a connection, a listener or a UDP socket, with everything it can do as methods (inside, the number the C++ side knows it by)

    The four modules split the work the same way:

    Module What is in it
    tcpconnections: listen, accept, connect, and request (one whole exchange)
    udpsingle messages: open, send, receive, sender
    socketthe type socket.Socket, whose methods are what every socket can do - send and receive text or bytes, close(), timeouts - plus socket.error() and socket.from_handle
    hostnames and addresses: host.address("example.org"), host.name()

    Opening a socket can fail - nobody listens, the port is taken, the name is unknown. Then tcp.listen, tcp.accept, tcp.connect and udp.open return nothing instead of a socket, and socket.error() says why.

    The module names are reserved in a program that imports "sockets": a variable cannot be called socket, tcp, udp or host (error S065). Call it connection, listener, sock ...

    2. TCP#

    Function Returns What it does
    tcp.listen(address, port): socket.Socketlistener, or nothingStarts waiting for connections. address "" means every address of this computer; port 0 lets the system choose (ask the listener's port()).
    tcp.accept(listener): socket.Socketconnection, or nothingWaits for the next caller and returns the connection to it (after set_timeout on the listener, also nothing when nobody came in time).
    tcp.connect(server, port): socket.Socketconnection, or nothingConnects to a listening program. nothing if nobody listens there, or the name is unknown.
    tcp.request(server, port, line): stringthe answer, or ""Connect, send one line, read one line, disconnect - a whole exchange in one call (written in Thunder, in sockets.th, with with).

    What every socket can do, as methods of socket.Socket (s is any socket):

    Method Returns What it does
    s.send(text): intbytes sent, or -1Sends the text (as UTF-8 bytes).
    s.send_line(text): intbytes sent, or -1Sends the text and a line break.
    s.receive(max_bytes): stringtext, or ""Waits for up to max_bytes of text.
    s.receive_line(): stringa line, or ""Waits for a whole line and returns it without the line break.
    s.send_bytes(data: byte[]): intbytes sent, or -1Sends raw bytes as they are (a file, a packet of a binary protocol).
    s.receive_bytes(max_bytes): byte[]bytes, or []Waits for up to max_bytes of whatever arrives, as a byte[]; see "Bytes" in the library reference.
    s.is_open(): boolTrue while the connection can still deliver something.
    s.close()Closes a connection, listener or UDP socket; the other side notices. with calls it for you (section 3); closing a socket twice does no harm.
    s.set_timeout(milliseconds): boolHow long tcp.accept, receive and udp.receive may wait; -1 (the default) means for ever. A listener's timeout is inherited by the connections it accepts.
    s.port(): intThe port on this computer (useful after tcp.listen(address, 0)).
    s.peer(): string"ip:port"Who is at the other end of a connection.

    And two functions of the module socket itself:

    Function Returns What it does
    socket.error(): stringWhy the last call that failed (nothing, -1 or "") did so: "Connection refused", "timed out", "closed by the other side", ...
    socket.from_handle(handle): socket.Socketsocket, or nothingThe socket for a number the C++ side returned (nothing for -1). The modules use it; so may a native library of your own that opens sockets.

    Lines are the natural unit. Most simple protocols are "one line each way": the client sends a line, the server reads it with receive_line(), answers with send_line. receive is for text that is not line-shaped; it returns whatever has arrived, up to the limit, and "" once the other side has closed.

    Waiting. tcp.accept, receive and receive_line wait until something happens - like input() waits for the user. A program that must not wait for ever sets a timeout:

    import "sockets"

# Reads one line, waiting two seconds at most.
func read_line(connection: socket.Socket): string
    connection.set_timeout(2000)                  # two seconds
    var line = connection.receive_line()
    if line == "" and not connection.is_open()
        println("the other side went away")
    else if line == ""
        println("nothing arrived: ", socket.error())  # "timed out"
    return line

    3. Closing sockets: with#

    A socket stands for something outside the program - a connection the other side is holding open, a port the system has lent out - so it must be given back when the program is done with it. with does that, through the socket's own close() method: the socket it opens is closed when the block ends, however it ends - at the end of the block, or by a return, break or continue that leaves it.

    import "sockets"

with connection = tcp.connect("localhost", 7000)
    if connection != nothing
        connection.send_line("hello")
# connection is closed here

    This is how tcp.request is written in sockets.th: an early return from inside the block still closes the connection, and the value is worked out before it is closed.

    import "sockets"

func request(server: string, port: int, line: string): string
    with connection = tcp.connect(server, port)
        if connection == nothing
            return ""
        connection.send_line(line)
        return connection.receive_line()           # read first, then closed
    • Nothing is not closed. When opening failed, the name holds nothing and the end of the block simply passes it by; test for nothing inside the block, as above.
    • Nested blocks close the innermost first: in the first example the connection is closed before the listener.
    • Closing twice does no harm. A program may still call close() itself inside the block (to let the other side see the end, say); the close at the end of the block then does nothing more.
    • A socket you already have goes in without a name: with listener closes listener at the end of the block.
    • The name is a constant inside the block: assigning to it is an error (S012).
    • Not closed: when the program stops with a runtime error or os.exit(). The operating system frees every socket of a process that ends, so nothing is left behind.

    with works for any struct that has a close() method - socket.Socket is one - and for a plain value, such as an int handle, returned by a module's function that has a close; the language reference and sample 39 (samples/en/39_with.th) show the whole statement. In Pashto the keyword follows the handle (اړیکه سره = ...), or the value when there is no handle (ساکټ سره, where it ends the line), as the language says it - "ساکټ سره", with the socket:

    4. UDP#

    Function Returns What it does
    udp.open(port): socket.Socketsocket, or nothingOpens a UDP socket on a port of this computer (0: any free port).
    udp.send(sock, server, port, text): intbytes sent, or -1Sends one message to server:port.
    udp.receive(sock, max_bytes): stringthe message, or ""Waits for one message.
    udp.send_bytes(sock, server, port, data: byte[]): intbytes sent, or -1A datagram of raw bytes.
    udp.receive_bytes(sock, max_bytes): byte[]bytes, or []A datagram as a byte[].
    udp.sender(): string"ip:port"Who sent the message udp.receive last returned - so a server can answer it.

    A UDP socket is a socket.Socket like any other: its set_timeout(), port() and close() methods work on it, and with closes it. (A datagram names its destination every time - the socket is just the stamp - so udp.send and its companions stay module functions that take the socket.)

    import "sockets"

with receiver = udp.open(0)
    with sender = udp.open(0)
        udp.send(sender, "127.0.0.1", receiver.port(), "a datagram")
        println(udp.receive(receiver, 100))       # a datagram

    UDP has no connection and no guarantee: a message may arrive late, twice or never. It suits things where the newest value matters more than every value - the position of a player in a game, a sensor reading every second.

    6. Two kinds of trouble#

    Something going wrong on the network is normal and is reported as a value: nothing instead of a socket, -1 or "", with socket.error() saying why. A program decides what to do about it - try again, tell the user, give up.

    A mistake in the program - using a socket after it was closed, calling tcp.accept on a connection instead of a listener, udp.send on a TCP socket - stops the program with runtime error R030 and a message such as socket.send_line: socket 0 is not open, exactly as a wrong built-in call would. Using the nothing a failed tcp.connect returned as if it were a socket stops it too (R033, "the value is nothing"). Those are bugs to fix, not conditions to handle.

    7. Running and packaging#

    • In the IDE, Run just works: thunder_sockets is built with the toolchain and found next to thundervm. Outside the IDE the same applies to thundervm program.thc.
    • A packaged program gets the library copied next to it automatically, because it is an ordinary native library (import native "thunder_sockets" in sockets.th): ship the directory, not only the executable.
    • To use sockets in a program of your own, just write import "sockets": the file is found in lib/thunder/<language> next to thunderc (copy it next to your program, or use -I <dir>, to pin another version).
    • The library uses the platform's own sockets - BSD sockets on Linux and macOS, Winsock on Windows - and nothing else. Its source, about 800 lines of C++, is a worked example of a native module that keeps state (the table of open sockets) between calls.
    • sockets.th is also the worked example of native functions inside a module: module socket declares native func _send(handle: int, text: string): int, and the C++ side registers that function under its qualified name, "socket._send" (and the Pashto "ساکټ._ولېږه"). The _ keeps these raw, number-taking functions private to their module; the public methods of socket.Socket, such as send, wrap them.

    A note on safety. A program that listens on "" (every address) can be reached from other computers on the network; on "127.0.0.1" only from the same machine. The usual rules of the native interface apply: the library runs with the rights of the process, and thundervm --no-native switches it (and every native library) off.

    Before 0.7 these were plain functions with prefixes - tcp_connect, socket_send_line, socket_close, host_address ... - and a socket was a bare int, with -1 for failure. 0.7 put each in its module under the short name (tcp.connect, socket.send_line(s, text), host.address), socket_open became socket.is_open, and request became tcp.request. Now the per-socket functions are methods of socket.Socket: socket.send_line(s, text) is written s.send_line(text), socket.close(s) is s.close(), and so on.
