    doing several things at once (docs/concurrency.md)

    import "concurrency" and every object below is yours (thunderc finds this file in lib/thunder next to itself, or name a directory with --module-path). Nothing here is native: it is ordinary Thunder, written to be read - open this file to see how a semaphore, a barrier, a channel and a wait group are really built, from the two primitives the virtual machine has to provide because they must be indivisible: the lock and the condition (module task).

    Task a piece of your program running beside the rest: Task(func() ...) Mutex / Lock mutual exclusion: "with m.lock()" unlocks at the end of the block Condition waiting inside a lock until something becomes true (a monitor) Semaphore a counted permit: at most n tasks inside at once Barrier nobody passes until every party has arrived Channel<T> sending values from one task to another, with a queue between them WaitGroup waiting for a group of tasks to finish Latch a gate that opens once, when its count reaches zero ReadWriteLock many readers together, or one writer alone timer timer.after(ms, action), timer.every(ms, action), Timer.cancel()

    Tasks share everything: globals, and any variable a closure of theirs captures. They take turns on one thread, switching every 100 instructions (thundervm --slice n), so two tasks never run at the same instant - but a switch can happen between the three instructions of "count += 1", which is why a shared counter still needs a lock. The schedule is the same on every run, so a program's output can be checked; --schedule-seed n varies it, reproducibly, to shake races out of a program.

    The program ends when every task has ended. If they all end up waiting for each other, the virtual machine says so and stops: "deadlock: ... (R037)".

    Mutex (mutual exclusion)

    The guard a lock hands out. "with" calls close() at the end of the block, however the block ends - a return or a break in the middle of a critical section can no longer leave the lock taken. Taking the guard apart yourself is never needed.

    Condition (a monitor)

    Something a task waits for inside a lock: "the queue is not empty", "every player is ready". wait() gives the lock back while it waits and takes it again before going on, so the state it waited for cannot change under it. Always wait in a loop - another task may have been woken first and changed the state back:

    with m.lock() while len(queue) == 0 not_empty.wait() var item = remove_at(queue, 0)

    Task

    A piece of the program that runs beside the rest. Making one starts it:

    var worker = Task(count_words) var other = Task(func() println("hello from ", task.name(task.current()))) worker.join()

    The action takes no arguments - a closure carries whatever it needs:

    for name in names var mine = name # one variable per round, captured by the closure push(workers, Task(func() greet(mine)))

    Channel (communication)

    A pipe between tasks, with room for 'capacity' values. send waits while it is full, receive waits while it is empty, so a fast producer cannot run away from a slow consumer. A capacity of 0 is a rendezvous: the sender waits until a receiver has taken the value from its hand.

    var jobs: Channel<string> = Channel(4) ... jobs.send("one") ... while jobs.has_next() work_on(jobs.receive())

    close() tells the receivers that nothing more will come: has_next() then answers false once the last value has been taken. Receiving from a channel that is closed and empty, or sending into a closed one, is a mistake in the program and stops it.

    timer

    setTimeout and setInterval, in Thunder: a timer is a task that sleeps and then does something. Because it is a task, the rest of the program keeps running while it waits.

    var tick = timer.every(100, func() println("tick")) task.sleep(350) tick.cancel()
