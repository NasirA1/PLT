    testing

    import "testing"

    the test framework, written in Thunder itself (docs/testing.md)

    Tests live in test files of their own. Mark each test with @test - a function, or a whole struct or module (a suite) - and run the file; the compiler finds the tests, imports this file and runs them, one after another, then prints the summary:

    import "lib/stack" # the code under test

    @test func adds_up() # shown as "adds up" expect.equal(2 + 2, 4)

    @test("a new stack") struct NewStack # a suite: every public method without parameters _stack: Stack<int> # is a test, run on a new NewStack each time

    NewStack() # the constructor prepares each test ... _stack = Stack()

    func is_empty() expect.is_true(_stack.is_empty())

    func close() # ... and close(), when there is one, tidies up pass

    A module can be a suite too (@test on the module: its public functions without parameters are the tests), and @test on a single method or function marks just that one, with an optional description: @test("pushes one item").

    A test file holds tests only - no statements of its own and no main() - and a program file may not use this module: test code stays out of production code.

    Every test prints one line - "✓ name" when it passed, "✗ name: what went wrong" for each expectation that failed - under its suite's name, and the summary ends the program with exit status 1 when any test failed (so a script, or the VS Code extension, can tell). Program arguments choose which tests run: "thundervm tests.thc adds" runs only the tests (or the suites) named on the command line - "suite/test" names one test of one suite - which is how VS Code's Test Explorer runs a single test or a single suite.

    Mocks. "@mock struct FakeClock: Clock" makes a stand-in for the interfaces the struct lists: every method of theirs records its calls, then answers with the struct's own method of that name, or, without one, does nothing and returns a default value (0, "", false, nothing, []). The struct has the Mock mixin's methods to ask what happened:

    interface Clock func hour(): int

    @mock struct FakeClock: Clock time: int # what the test wants the clock to say func hour(): int return time

    @test func says_good_morning() var clock = FakeClock(time: 9) expect.equal(greeting(clock), "Good morning") clock.expect_called("hour", 1)

    Nothing here is native: this is ordinary Thunder, written to be read.
