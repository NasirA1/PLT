    راوړه "concurrency"

    څو کاره په یوه وخت کې (docs/ps/concurrency.md)

    راوړه "concurrency" ولیکئ او ټول لاندې شیان ستاسې دي (thunderc دا فایل د ځان تر څنګ په lib/thunder کې مومي، یا یوه پوښۍ د --module-path سره ورکړئ). دلته هېڅ بهرنی نشته: دا ساده تندر دی، د لوستلو لپاره لیکل شوی - دا فایل پرانیزئ او وګورئ چې سیمافور، خنډ، کانال او د انتظار ډله رښتیا څنګه له هغو دوو بنسټیزو شیانو جوړېږي چې مجازي ماشین یې باید ورکړي، ځکه چې باید نه‌وېشل‌کېدونکي وي: قلف او حالت (ټولګی کارونه).

    کار ستاسې د پروګرام یوه برخه چې د نورو تر څنګ ځي: کار(دنده() ...) قلف / ساتونکی یوازې یو کار دننه: «_قلف.قلف_کړه() سره» د بلاک په پای کې خلاصوي حالت د قلف دننه انتظار، ترڅو څه رښتیا شي (مانیټر) سیمافور شمېرل شوې اجازه: په یوه وخت کې تر ډېره n کاره دننه خنډ هیڅوک نه تېرېږي ترڅو ټول ګډونوال ورسېږي کانال<ت> له یوه کاره بل ته د ارزښتونو لېږل، د لیکې سره په منځ کې ډله د یوې ډلې کارونو د پای انتظار دروازه یوه دروازه چې یو ځل پرانیستل کېږي، کله چې شمېر صفر شي لوست_لیک_قلف ډېر لوستونکي یوځای، یا یو لیکونکی یوازې مهالګر مهالګر.وروسته(ملي_ثانیې، چار)، مهالګر.هر_ځل(...)، مهالګر.لغوه_کړه()

    کارونه هرڅه شریکوي: عام متغیرونه، او هر هغه متغیر چې د دوی یوه تړلې دنده یې نیسي. پر یوه مزي وار په وار ځي او هرو ۱۰۰ لارښوونو وروسته بدلېږي (thundervm --slice n)، نو دوه کاره هېڅکله په یوه شېبه کې نه ځي - خو بدلون د «شمېر += ۱» د درېیو لارښوونو تر منځ هم کېدای شي، او همدا لامل دی چې یو شریک شمېرګر لا هم قلف ته اړتیا لري. وارۍ په هر ځل کې یو شان دي، نو د پروګرام وتنه ازمویل کېږي؛ --schedule-seed n یې بدلوي، خو بیا هم په تکرارېدونکې توګه، چې د پروګرام ننګونې راوباسي.

    پروګرام هغه وخت پای ته رسېږي چې ټول کارونه پای ته ورسېږي. که ټول یو بل ته انتظار پاتې شي، مجازي ماشین وايي او دروي یې: «بند کرښه: ... (R037)».

    کانال (اړیکه)

    د کارونو تر منځ یوه نلۍ چې د «ظرفیت» ارزښتونو ځای لري. ولېږه هغه وخت انتظار باسي چې ډکه وي، واخله هغه وخت چې تشه وي، نو چټک جوړوونکی له ورو کاروونکي مخته نشي تښتېدای. د ۰ ظرفیت یو لاس په لاس دی: لېږونکی انتظار باسي ترڅو یو اخیستونکی ارزښت له لاسه واخلي.
